# 使用AI恢复授权客户端协议：可执行工作流

本流程适用于自有/已授权客户端与自建测试服务。旧服务端专有规则未必在客户端中存在，必须把“客户端消费结构”“本地服务策略”“原客户端运行验证”分开。

## 一、先给AI一个有限问题

不要只说“恢复全部协议”。用一个可判定切片：

```text
本轮只处理等待房间的设置更新。
复用现有帧解码器、账号会话和建房逻辑。
找出请求/回复的字段、允许阶段、广播对象与失败路径。
不要改登录或创建另一个房间实现。
交付：解析器、授权/事务处理、合成测试、最小原客户端验证。
未知字段保持原字节，不用零值冒充已恢复。
```

## 二、按消费者找参数用途

1. 记录实际按钮操作与请求时间，只采这一族的ID/长度/阶段。
2. 找发送函数，确认结构长度、字节序、字符串编码、身份来源及条件分支。
3. 找注册表中同方向/同阶段的接收消费者。同一个ID在不同上下文可能不同。
4. 跟到真正读取字段的函数，区别复制、保存、显示和实际副作用。
5. 汇总同构记录，写一个通用解析器；仅对首次差异和离群样本追加实验。

不要把工具猜出的类名、函数名、地址相近或“能编译”作为语义证明。虚调用目标未闭合就明示未知。

## 三、一个协议族必须交付什么

| 层 | 交付要求 |
|---|---|
| 帧 | 半包/粘包、长度上界、错误输入拒绝、消息边界 |
| 布局 | 方向、连接阶段、ID、定长/变长、计数、字符串终止、尾部保留 |
| 授权 | 当前会话、账号、房主/成员/物品归属，不信客户端自报身份 |
| 状态 | 哪些阶段允许；重复请求如何处理；失败不得留下半状态 |
| 存储 | 事务提交、唯一键、余额/扣量、重启后的语义 |
| 回复 | 本人、房间成员、其他连接的接收范围，避免副作用重复 |
| 验证 | 合成边界测试＋原客户端看到/发生了什么 |

## 四、最低成本测试顺序

- 首先无客户端测试：合法/非法长度、缺NUL、越界计数、伪造UID、退休连接、重复请求、事务回滚。
- 使用同一函数族的代表样本，不逐条重做所有动作。
- 再用原客户端做一个最短路径，比较服务日志与界面/状态。
- 有歧义时只记录必要字段与首次分歧，不每轮抓全进程转储或全量素材。
- 同一版本输入未变，复用已经通过的测试与证据；一批结束再做整套回归。

测试中的临时账号属于合成夹具。实际用户是否使用隔离测试账号应遵从用户选择，不擅自复制或修改真实账号数据。

## 五、本项目可直接练习的入口

- `server/tests/test_local_service.py`：基础帧、连接状态与服务闭环。
- `server/tests/test_room_settings.py`：房主权限、设置原子更新、准备重置、密码不进入目录。
- `server/tests/test_shop_purchase.py`：报价不可信、原子扣款/授予和回放边界。
- `server/tests/test_rankings.py`：字段恢复和本地排序策略分离。
- `server/tests/test_sdo_service.py`、`client-adapter/tests/`：挑战、错误密码、重放、身份与密钥。

这些测试不需要真实资源包。已有代码通过不等于旧服规则已恢复；例如同分按UID排序只是本地选择。

## 六、常见错误

- 按“请求ID+1”猜回复，忽略通用封装和内部子消息。
- 把空列表当全部功能成功，隐藏未配置或缺失数据。
- 仅做自己编码再自己解码，双方一起写错仍会通过。
- 请求成功但没改数据库，或数据库改了却漏发客户端通知。
- 给所有进程共享会话，或复用旧PID/旧就绪文件。
- 把HTTP认证、游戏TCP、P2P UDP混作一个协议。
- 把必须在UI线程发生的初始化放进任意工作线程。
- 把真实账号库、密码、Cookie、私钥或全量原始资料提交到公开仓库。

## 七、交给AI的审查清单

```text
请只审查本次改变的协议族：
1. 哪些字段有实际消费者支持？哪些仍是本地策略？
2. 是否拒绝错误长度/编码/计数，保留未知尾部？
3. 是否验证当前会话与操作归属，而不是只检查payload里的UID？
4. 失败时数据库、余额、成员表和通知队列是否仍一致？
5. 重复请求会不会重复扣量/建人/发奖？
6. 是否把仅静态恢复、服务测试和客户端验证混称完成？
7. 日志/发布文件有没有凭据或专有载荷？
列出可复现的问题；没有证据不要猜测成故障。
```

## 八、发布时

使用源码白名单建立新历史，公开自行编写的实现、说明与合成测试。原软件、素材、数据库、IDA/PDB、真实trace及任何凭据保留在授权本地环境。发布扫描不是授权证明，公开可见也不自动授予开源许可。
