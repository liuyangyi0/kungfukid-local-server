# 原登录窗口兼容模块实现说明

> 公开版扩充：2026-09-17。基于现有源码讲解，不保证其他客户端版本兼容。
> 从零接线先看 [部署操作手册](DEPLOYMENT_WALKTHROUGH.md)。
> 适用范围：受信任本地环境中的原版32位SDK与自建账号服务。当前只有隔离VM实测，不是任意电脑即装即用的发行包。

## 1. 要实现的效果

保留原登录窗口，让用户输入本地注册的账号密码，由自建服务真实校验，再让原客户端自然进入大厅。

兼容模块只负责三个接口边界：认证请求去哪里、密码控件使用哪个输入实现、密码封装使用哪个公钥。它不代替账号数据库，不直接调用“登录成功”，也不修改战斗状态。

当前最重要的区别：**不是让服务对任意密码返回成功，而是把原SDK接到自己的认证系统。**

```text
启动本地服务 → 生成本轮密钥 → 发布公钥及服务就绪信息
                                  ↓
启动游戏 → 发现它创建的SDK进程 → 加载请求适配与用户态输入模块
                                  ↓
用户在原框输入密码 → 原SDK封装 → 本地服务解封装并校验账号密码
                                  ↓
绑定账号与本机游戏进程 → 原SDK成功回调 → 原生选区/人物/大厅流程
```

这三个模块以外，客户端仍依赖已有离线GPK适配、游戏登录地址配置和角色表就绪检测。只启动HTTP服务不足以完成整条链。

## 3. 先固定适用版本，而不是先改地址

当前逻辑对应`sdologin.exe`、`duilib.dll`和`SdoBaseClient.dll 2.2.2.0`的已分析组合，目标进程是i686。更新缓存中的另一版SDK不能按同一布局处理。

现有检查包括：目标映像路径、游戏与SDK父子关系、进程创建时间、主映像基址、指定导出位置、密码控件虚表和密码store虚表。它们不是完整的发行版模块身份清单；当前适配器自身的路径检查也存在实验室硬编码。

迁移版本时必须重新确认三类契约：

1. 模块契约：导入/导出名称或序号、位数、实际模块版本。
2. 对象契约：字段偏移、类型、构造时机及所属对象。
3. 调用契约：调用约定、隐藏返回参数、线程及原函数副作用。

以下偏移表全部使用**十进制字节偏移**，只适用于该组合。不要把它们当成Windows标准接口，更不能拿去修改其他程序。

## 4. 启动器怎样加载这些模块

### 4.1 现有启动顺序

1. 读取已准备好的`deployment.json`。
2. 确认没有默认外部路由；确认四个端口属于该部署收据中的服务进程。
3. 拒绝与已有游戏/SDK进程混跑，不以模糊进程名任意结束进程。
4. 将旧角色表收据移入本轮记录，然后从正确工作目录启动`gfxz-lab.exe`。
5. 查找它实际创建的`sdologin.exe`，要求父PID匹配且候选唯一。
6. 用已有`kk_inject.exe`把请求适配DLL加载到**SDK进程**，等该PID的`stage=ready`。
7. 加载输入模式DLL，等该PID的`user_mode_event_adapter_ready`。
8. 当前实验启动器还加载接口名探针，并把角色表观察器加载到**游戏进程**。
9. 写出本轮`awaiting_user_password`收据，交给用户手动登录。

`kk_inject.exe`只是现有的DLL加载工具，不负责构造认证成功结果。这里复用它，不要求使用者重新写一套远程进程加载器。不要把SDK适配模块误加载进主游戏进程。

### 4.2 DLL加载后的工作

当前DLL在`DLL_PROCESS_ATTACH`禁用线程通知并创建工作线程，实际安装操作在工作线程中执行；输入控件的改变还会切回UI线程。

它们会保留原函数地址，再安装有限的IAT/虚表转发。所谓“不修改原SDK磁盘文件”，**不等于完全不写运行内存**：当前实现确实修改了导入槽、一个共享虚表槽，以及已经校验的输入模式/公钥字段。

引用这些槽的DLL不能在函数指针仍被使用时卸载。当前按进程生命周期加载，并没有完整热卸载协议。

### 4.3 使用现有实验入口

原实验双击入口没有作为通用安装器发布。请按 [部署操作手册](DEPLOYMENT_WALKTHROUGH.md) 准备服务与客户端，不直接运行未配置的模板。

如果要自己实现可迁移启动器，应该把上面的流程整合成“服务准备→模块准备→等待用户”的状态机。不要只写一个`Start-Process`后固定睡几十秒，再假定模块已经安装成功。

## 5. 模块一：把认证请求转到本地服务

### 5.1 为什么有两层重定向

只在`getGuid`之前改地址不够：原SDK可能在此之前查询账号类型。因此现有实现同时处理两层。

| 层级 | 安装位置 | 当前动作 |
|---|---|---|
| SDK认证对象 | `sdologin.exe`对SdoBaseClient序号16的导入槽 | 发起动态密钥请求前，更新对象主备地址和端口，再调原函数 |
| 公共HTTP连接 | `SdoBaseClient.dll`的`InternetConnectA`导入槽 | 将该模块的连接目标定向到`127.0.0.1:18082` |
| HTTP请求路径 | 同模块的`HttpOpenRequestA`导入槽 | 将`authen/...`补为`/authen/...`，随后调用原函数 |

认证对象中，主/备地址字符串位于`+4/+36`，端口位于`+32/+64`。现有代码调用该模块自己的字符串赋值函数，不用外部编译器的`std::string`覆盖它，以免破坏字符串布局和堆所有权。

公共连接适配的核心只是改变目标并转发原调用，示意如下；完整签名、安装及回滚以源码为准：

```cpp
return original_connect(
    handle, "127.0.0.1", 18082,
    user, password, service, flags, context);
```

这里的`user/password`是该API原有参数，原样转发，不输出到日志。

### 5.2 IAT替换的操作顺序

现有`replace_import`执行：

1. 读取目标模块PE导入目录，匹配DLL名。
2. 按导出序号或导入名称找到对应槽，不用猜测所有同名函数的地址。
3. 暂时允许该指针槽写入，保存原地址，写入适配函数地址。
4. 恢复页保护。
5. 如果后续必需hook安装失败，尝试回滚已经安装的槽，不报告ready。

这不是修改函数机器码的跳转补丁。它只覆盖经过匹配的导入调用；不代表所有网络库、所有进程或所有更新请求都已被拦截。其他模块的连接必须另有证据和配置，隔离网络仍是必要边界。

当前`HttpOpenRequestA`适配会清除安全连接标志，因为接的是本机HTTP服务。**不得把这一实现改个IP就用于远程明文认证。**跨机器版本需要单独设计加密通道，而不是关闭TLS验证。

### 5.3 本地HTTP服务要实现哪些接口

| 接口 | 作用 | 是否授予登录 |
|---|---|---|
| `checkAccountType.json` | 返回本地账号采用密码登录的策略元数据 | 否；现有回复不是账号存在性证明 |
| `getGuid.json` | 发放与SDK/game身份绑定的一次性挑战 | 否 |
| `staticLogin.json` | 校验挑战、解封装、真实密码校验、绑定游戏身份 | 只有完整成功后才授予 |
| `getPromotionInfo.json` | 校验已经绑定的会话，返回空推广链接 | 否；不创建新会话 |

原SDK需要顶层`return_code`字符串、`return_message`字符串和`data`对象。`data`内为扁平字符串字段。不要把内部消费者的`resultCode`误写成顶层字段，也不要只返回HTTP 200就当作成功。

`getPublicKey.json`曾在失败回退路径出现，但当前主路径不依赖它，尚未作为完整接口接入。看到它不能直接断定私钥丢失；先检查主请求地址、路径、挑战和实际返回状态。

## 6. 模块二：切换为可用的用户态密码输入

### 6.1 保留什么、改变什么

保留原窗口、密码遮罩和SDK密码封装。改变的是旧强保护输入provider，不是把密码变为明文显示，也不是隐藏风险弹窗后继续冒充成功。

当前代码调用原导出函数：

```cpp
SetPasswordMode(edit, true);        // 保留密码遮罩
SetStrongPasswordMode(edit, false); // 使用内置普通/用户态路径
```

这是说明性写法。实际函数是原DLL导出的`__thiscall`成员函数，必须用正确函数指针类型调用，不是两个全局C函数。

### 6.2 怎样找到正确控件

原窗口类为`igwUserPwdLoginDialog`。在当前SDK进程内枚举窗口，要求唯一匹配；通过`GWLP_USERDATA`取得窗口对象，并检查对象`+4`确实指向该HWND。

窗口对象`+876`提供密码`CSdoEditUI`。继续验证其虚表是否为`duilib.dll`导出的目标类型虚表，然后才能访问如下字段。

| 对象 | 字段 | 含义/用途 |
|---|---|---|
| CSdoEditUI | `+1128` | strong模式字节 |
| CSdoEditUI | `+1285` | 密码遮罩字节 |
| CSdoEditUI | `+1276` | 输入控制器指针 |
| 输入控制器 | `+60` | 已初始化标记 |
| 输入控制器 | `+64` | 输入provider失败后保留的锁 |
| 输入控制器 | `+92/+188` | 当前provider/请求provider，当前用户态路径为1 |
| 输入控制器 | `+104/+108/+112/+116` | store及相关对象指针，先验证存在 |
| 输入控制器 | `+200` | 实际只读属性；本适配不清除它 |

这些字段不是通过搜索密码字符串定位的。适配器不读取密码框文字，不记录按键字符。

### 6.3 为什么必须在UI线程做

输入控件由UI线程维护。当前模块临时接管目标窗口过程，注册私有窗口消息，使用`SendMessageTimeoutW`让处理函数在该窗口线程中调用原模式设置函数，之后恢复窗口过程。

已有实验中，仅`PostMessage`并没有保证该设置被原SDK处理。因此启动器必须等实际执行收据，不把“已投递消息”当作“已切换模式”。超时也不能继续强写一串控件字段。

### 6.4 为什么只调用SetStrongPasswordMode还不够

原provider初始化失败时会设置`controller+64=1`；后来用户态对象已经初始化，也可能遗留此锁，字符处理仍然被抑制。

现有适配只在下列条件全部满足后把该失败锁从1清为0：已初始化、当前及请求provider均为1、四个相关对象非空。`+200`只读属性不改变。未知值不能一律清零。

另一问题是返回登录页时控件可能重新建立。因此当前`DoEvent`适配不再只比较第一次保存的指针，而是按当前窗口拥有关系和虚表重新确认目标密码控件。

该虚表槽在本版为索引68。槽本身属于共享类虚表，但wrapper只调整通过校验的密码控件，其他控件照常转发；原事件恰好调用一次，事件参数作为不透明对象传递，不解析键值。

目前新启动登录已实测；“登录→退出→同进程重新输入”的全部重入组合尚未完成验收。发布时应补这组测试，而不是将首次登录成功扩大为整个控件生命周期稳定。

## 7. 模块三：配置自建服务的公钥

### 7.1 不是获取旧服务私钥

服务生成自己的RSA密钥对。客户端用自己的公钥封装，服务用配对私钥解封装。原SDK封装逻辑保留，不需要恢复旧运营方的私钥。

当前兼容记录使用1024位RSA、指数3和原格式填充，这是旧格式兼容约束，不是推荐的新系统安全方案。它只在受限回环环境使用，不应直接暴露为公网认证入口。

服务端当前生成公钥记录的逻辑为：

```python
key = rsa.generate_private_key(public_exponent=3, key_size=1024)
public = key.public_key().public_numbers()
record = (
    struct.pack('<H', 1024)
    + public.n.to_bytes(128, 'big')
    + public.e.to_bytes(128, 'big')
)
```

记录长258字节：2字节LE位数、128字节BE模数、128字节BE指数。`public-key.bin`不是PEM文件，不能把PEM文本直接复制进对象。

服务私钥仅存在进程内存，不写入公钥文件或数据库。部署控制面将该服务运行目录的公钥复制为`active-public-key.bin`，适配器安装时读取它。

### 7.2 在什么时机安装公钥

现有模块包装原`GetPasswordText`导入。在真正生成密码记录之前：

1. 从CSdoEditUI取得输入控制器。
2. 检查当前provider为1。
3. 从控制器`+104`取得store。
4. 检查store虚表等于当前duilib的目标虚表。
5. 将258字节自建公钥复制到store的`+40`。
6. 完整调用原`GetPasswordText`，让原SDK完成封装。

成功标记为`own_key_applied_to_password_store`。这个标记只能证明公钥写到了通过检查的对象，不能单独证明密码认证成功。

旧实验曾直接改SDK磁盘文件的公钥/配置，触发登录器更新错误；当前使用启动后的对象适配，不继续原地改写SDK磁盘文件。

### 7.3 调用约定不能弄错

原函数返回客户端自己的字符串对象，包含隐藏的返回缓冲区参数；不是简单的`char* getPassword()`。

当前x86 wrapper用`__fastcall`接收`this`及占位EDX参数，并保留隐藏返回缓冲区、动态密钥和长度，再按原`__thiscall`签名转发。错误签名可能表现为乱码、栈损坏或随机崩溃，不能通过增加延时修复。

### 7.4 密钥生命周期必须同步

当前服务每次启动会生成新密钥，而DLL在加载时只读一次公钥。因此：

- 同一服务内重复登录可复用这对密钥，但每次认证必须取得新挑战。
- 服务重启后，旧SDK进程内的公钥不会自动更新。
- 必须同步新的`active-public-key.bin`，并重新准备SDK模块；当前可靠路径是启动新客户端。
- 不要因为不想重启就导出服务内存中的私钥，也不要把旧公钥文件当作仍然匹配新服务。

迁移版启动器可以增加显式公钥版本握手，但目前代码没有实现通用热更新协议。

## 8. 服务端如何确认它真的是正确密码

公钥适配只解决“服务能否读懂原SDK记录”，之后还要真实认证。

当前处理顺序：

1. `getGuid`生成20位数字动态密钥和随机guid，绑定已核验的SDK/game进程身份，30秒有效。
2. `staticLogin`先消费该挑战，失败或并发重放也不能重复使用。
3. 对账号及密码记录做原外层Base64/TripleDES-CBC解码。
4. 校验164字节内层记录的版本、类型、长度、校验和、14字节尾部。
5. 使用服务自有私钥解密128字节RSA部分，确认解密内容的挑战前缀匹配。
6. 调用现有`AuthManager.login`，对SQLite账号密码摘要进行真实scrypt校验。
7. 再核验SDK/game身份，选择本地区服并绑定账号会话与游戏进程；任何后续交接失败都撤销这次新会话。
8. 最后才序列化成功字段与会话Cookie，让原SDK触发自己的正常回调。

外层IV曾是实际错误来源：磁盘静态字节与运行值不同。当前有效IV为`23456789`，依据固定非凭据全局采样纠正；没有读取用户密码来推断它。单纯“自己加密再自己解密”的往返测试无法发现两端共同写错的IV。

原窗口当前只验证并接纳12–30字节可打印ASCII密码子集。独立本地注册API支持的范围更宽，不能因此声称原SDK也支持所有Unicode或长密码；发行包需要把两者的限制统一。

## 9. 认证成功后还需要什么

| 条件 | 为什么需要 |
|---|---|
| 游戏登录地址指向本机兼容端口 | SDK的HTTP认证地址不等于游戏TCP地址 |
| 账号与游戏进程绑定 | 不接受任意进程伪造旧SDK密文来领取角色资料 |
| 原角色配置表就绪 | 避免在表为空时创建人物导致崩溃 |
| 游戏TCP及P2P服务 | HTTP成功不等于大厅、房间和P2P初始化完成 |

当前端口分工：17999为本地账号API，18082为原SDK HTTP，18000为登录兼容TCP，18001为游戏TCP和P2P UDP。都属于隔离VM内的本地服务，不连接旧运营服务。

`WindowsSdkVerifier`由连接拥有者找到SDK，再核验它的游戏父进程、映像路径和创建时间。这个方法只适用于同机环境；它不是跨机器登录协议。

注意，认证层进程绑定不等于就绪文件绑定。当前`ReadyFile`只检查`kk-roleprop-ready.txt`的mtime和指针格式/范围；文件不含PID、创建时间或RunId。移走旧收据是启动器的基础防错步骤，不是强身份验证。教程不再声称该文件已证明属于当前客户端。

## 10. 构建与接线方法

公开版已用Windows x86编译环境构建四个兼容DLL；以`client-adapter/build.cmd`选项为准。不使用x64 DLL注入32位SDK。已有源码可直接作为构建输入，输出使用独立目录，不能覆盖正在运行的DLL或既有实验产物。

下面命令在已初始化的x86开发环境中执行，输出到`build/adapter`；不会自动安装或运行客户端：

```bat
client-adapter\build.cmd
```

构建输出包括四个DLL和自行编写的加载工具。编译通过不代表当前客户端版本兼容。

公开版不提供原实验bundled运行时或部署包。请为隔离VM准备Python及`requirements.txt`依赖；命令见 [部署操作手册](DEPLOYMENT_WALKTHROUGH.md)。

当前启动器引用`input-provider-a07.dll`等实验文件名。换成统一产物名时必须同步启动器配置，不能只重命名DLL就宣布部署完成。

## 11. 搬到另一台电脑前，应补哪些工程能力

以下是迁移工作建议，不是当前代码已经具有的功能，也不是另一套持久任务清单。

1. **路径配置化。** 客户端根目录、服务根目录、公钥和日志路径改由启动配置传入；保留解析后的精确路径校验，不简单删除现有白名单。
2. **模块版本清单。** 发布时固定目标SDK组合和本轮工具身份；不在每次点击登录时全量扫描游戏资源。
3. **启动协调。** 服务就绪后发布配套公钥，再加载适配器；用本轮PID和就绪事件拒绝旧收据。
4. **权限与回滚。** 仅控制自己启动的进程，hook安装失败停止并恢复已修改槽；不要自动关闭未知安全软件或提升全机策略。
5. **去除诊断负担。** 接口名探针可从日常启动移除；角色表就绪协调目前仍必要，不能与纯诊断一起删掉。
6. **存档迁移。** 复制数据库应采用停服复制或SQLite备份接口；不要把实验VM凭据、登录票据和私钥打进分发包。
7. **完整生命周期。** 验证首次登录、失败重试、回到登录页、SDK窗口重建、服务重启和游戏退出。当前一次成功不等于这些路径都稳定。

另一台电脑独立离线运行，可以在那台电脑上运行同样的本地服务。多台电脑共享中央服务则需要另做网络会话凭据桥、受保护传输和多人协议；不能只把127.0.0.1替换为远程IP，更不能让远程服务器信任客户端自报PID。

## 12. 怎么验证与定位失败

### 12.1 自动测试

使用仓库提供的Python运行相关测试，不输入真实密码；测试内使用合成凭据：

```text
python -m unittest server.tests.test_sdo_service -v
python -m unittest discover -s client-adapter/tests -p test_sdo_password_bridge.py -v
python -m unittest discover -s client-adapter/tests -p test_sdo_outer_password_codec.py -v
```

至少覆盖：错误密码拒绝、挑战过期/重放拒绝、身份不匹配拒绝、原协议字段与字节序、服务绑定失败回滚、推广接口不能创建新授权。只测成功路径不够。

### 12.2 原窗口观察

| 标记或现象 | 能说明什么 | 不能说明什么 |
|---|---|---|
| `stage=ready` | 当前请求适配安装成功 | 用户已经登录 |
| `user_mode_event_adapter_ready` | 目标输入事件适配已安装 | 所有重入路径都正确 |
| `own_key_applied_to_password_store` | 公钥已装入匹配store | 密码校验通过 |
| `guid: ok=true` | 动态挑战请求完成 | 用户身份已经认证 |
| `password: ok=true` | 服务端真实认证及当前绑定成功 | 后续房间/战斗都完成 |
| `authenticated_sdk_grant`及大厅报文 | 认证已经交接到游戏链 | 多人同步与结算完成 |

出现风险提示：先检查控件身份、provider、失败锁及是否发生控件重建，不要先怀疑账号密码。

出现通用认证失败：该提示有意合并身份、挑战、封装和密码错误，不能据此要求用户反复改密码。先看最后完成的阶段，再检查非敏感参数，例如接口名、模块版本、公钥配套关系和IV。

出现人物读取崩溃：回查角色表就绪及人物下发顺序，不回头修改SDK成功回调。

日志只记录阶段、PID、接口名、成功/失败及明确的非敏感参数。不记录完整URL查询、账号密码、密文认证请求、会话token、Cookie或RSA明文；原账号库也不回传到宿主或云端。
